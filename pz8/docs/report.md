# Отчёт по практической работе №8

**Тема:** подключение приложения FastAPI к реляционной базе данных.

**Индивидуальная тема:** планировщик событий.

**Дата выполнения:** 23.10.2026.

## 1. Цель работы

Освоить настройку SQLite и библиотеки SQLModel, создание таблиц и выполнение
операций CRUD из приложения FastAPI. Обеспечить сохранение данных при
перезапуске и подготовить приложение для запуска в Docker.

## 2. Постановка задачи

Исходное приложение из ПЗ №7 хранило события в списке, пользователей — в
словаре. После завершения процесса данные терялись. В ПЗ №8 необходимо:

1. Настроить подключение к SQLite.
2. Описать структуру БД средствами SQLModel.
3. Реализовать создание, чтение, обновление и удаление записей.
4. Сформировать два набора команд для работы с записями.
5. Проверить результат и подготовить отчёт.

Дополнительное условие: подготовить запуск в Docker, не обращаясь к
Docker-сокету в процессе выполнения работы.

## 3. Используемые средства

Приложение реализовано на Python, FastAPI, SQLModel, SQLAlchemy и Pydantic.
База данных — SQLite; драйвер sqlite3 входит в стандартную библиотеку Python.
HTTP-сервер — Uvicorn. Подготовлены Dockerfile на базе `python:3.12-slim`
и файл Docker Compose. Для проверки использованы unittest, TestClient,
временные файлы SQLite и curl.

Проверки выполнены на Python 3.14.4 с FastAPI 0.161.1, SQLModel 0.0.48,
SQLAlchemy 2.1.6, Pydantic 2.14.1, Uvicorn 0.54.0 и HTTPX 0.28.1.
Синтаксис исходников дополнительно проверен на совместимость с Python 3.12.
Запуск непосредственно в образе Python 3.12 не выполнялся.

## 4. Структура базы данных

Основная сущность индивидуальной темы — событие. Для постоянного хранения
регистрации добавлена также таблица пользователей.

### Таблица events

| Поле | Тип SQLite | Назначение |
| --- | --- | --- |
| id | INTEGER PRIMARY KEY | Идентификатор события, по умолчанию назначается SQLite |
| title | VARCHAR NOT NULL | Непустое название события |
| image | VARCHAR NOT NULL | Адрес или имя изображения |
| description | VARCHAR NOT NULL | Описание |
| tags | JSON NOT NULL | Список строковых тегов |
| location | VARCHAR NOT NULL | Непустое место проведения |

Ограничения на длину строк и тип элементов списка проверяются моделью
запроса Pydantic. JSON-тип хранит список тегов без ручного преобразования
в строку в обработчиках API.

### Таблица users

| Поле | Тип SQLite | Назначение |
| --- | --- | --- |
| id | INTEGER PRIMARY KEY | Идентификатор пользователя |
| email | VARCHAR NOT NULL | Уникальный индекс по email |
| password_hash | VARCHAR NOT NULL | Хеш scrypt с индивидуальной солью |
| events | JSON NOT NULL | Снимок списка событий, переданного при регистрации |

Поле `users.events` сохранено для совместимости с предыдущей работой.
Это JSON-снимок без внешнего ключа: удаление или изменение строки в `events`
не изменяет этот список. Владение событиями и разграничение доступа
не являются частью реализованной модели.

## 5. Подключение и жизненный цикл

В `planner/database/connection.py` создаётся engine с URL SQLite. Локальное
значение по умолчанию — `sqlite:///./data/planner.db`, в контейнере —
`sqlite:////app/data/planner.db`. Настройка доступна через `DATABASE_URL`.

Параметр `check_same_thread=False` разрешает использование SQLite из потоков,
которыми FastAPI выполняет синхронные обработчики. Для каждого HTTP-запроса
создаётся отдельный объект `Session` через `Depends(get_session)`.
После обработки запроса сеанс закрывается.

При запуске приложения контекст lifespan вызывает `conn(engine)`.
Функция создаёт каталог данных и таблицы через
`SQLModel.metadata.create_all(engine)`. При остановке освобождается пул
соединений. Таблицы импортируются до вызова `create_all`.

`create_all` подходит для первоначальной схемы этой работы; изменения
существующих таблиц и миграции схемы отдельно не реализованы.

## 6. Реализация CRUD

Модель таблицы `Event` наследует SQLModel с `table=True`.
Отдельные схемы `EventCreate`, `EventRead` и `EventUpdate` используются для
проверки входных данных и формирования ответа.

### Создание

`POST /event/new` проверяет поля, создаёт ORM-объект и выполняет
`session.add`, `session.commit`, `session.refresh`.
Ответ содержит сообщение и назначенный ID. Можно передать положительный
ID явно для совместимости с ПЗ №7. Конфликт первичного ключа вызывает
откат транзакции и HTTP 409.

### Чтение

`GET /event/` выполняет `select(Event)` с сортировкой по ID.
`GET /event/{id}` использует `session.get(Event, id)`.
Пустая таблица возвращается как `[]`, отсутствующее событие — HTTP 404.

### Обновление

`PUT /event/edit/{id}` загружает запись по первичному ключу, получает
переданные поля через `model_dump(exclude_unset=True)`, применяет изменения
и фиксирует транзакцию. В ответ возвращается полное обновлённое событие.
Пропущенные поля сохраняются. Пустой список тегов допустим.
Явный `null`, изменение ID и неизвестные поля отклоняются с HTTP 422.

### Удаление

`DELETE /event/delete/{id}` удаляет найденную запись и фиксирует изменение.
Повторное удаление возвращает 404. `DELETE /event/` удаляет все события,
не затрагивая пользователей. Старый путь `DELETE /event/{id}` сохранён.

### Пользователи

Регистрация сохраняет пользователя в SQLite. Уникальность email обеспечена
индексом БД; повторная регистрация возвращает 409. Пароли хешируются scrypt
с индивидуальной случайной солью. Вход сравнивает вычисленный хеш с сохранённым:
верные данные — 200, неизвестный email — 404, неверный пароль — 403.
Токены и пользовательские сессии не создаются.

## 7. Запуск в Docker

Команда запуска из каталога проекта:

```bash
mkdir -p data
LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)" docker compose up --build -d
```

Документация API: `http://localhost:8081/docs`.

Образ устанавливает зависимости и запускает Uvicorn на `0.0.0.0:8080`
от непривилегированного пользователя `appuser`. Docker Compose задаёт UID/GID
пользователя компьютера, публикует порт 8081 на `127.0.0.1` и подключает
каталог `./data` в `/app/data` (bind mount). Файл SQLite доступен на компьютере
как `./data/planner.db`; его можно открыть напрямую в SQLite Browser.

Обычная остановка и повторное создание контейнера сохраняют данные:

```bash
docker compose down
docker compose up -d
```

Для просмотра журналов используется `docker compose logs -f planner`.
Проверка здоровья контейнера запрашивает `GET /event/`, проверяя одновременно
HTTP-сервер и доступ к SQLite. Команда `docker compose down -v` не удаляет bind mount: данные остаются в `./data`.

По условию пользователя Docker-сокет не использовался. Контейнер не собирался
и не запускался. Docker-конфигурация подготовлена; YAML разобран программно.
Проверки приложения проводились отдельно от Docker.

## 8. Два набора команд

### Набор 1 — полный жизненный цикл события

Полные команды находятся в `scripts/demo-crud.sh`.

```bash
BASE_URL=http://localhost:8081 bash scripts/demo-crud.sh
```

Последовательность: создать семинар по SQLite, получить выданный ID,
просмотреть список и отдельное событие, изменить локацию и теги,
удалить созданное событие, проверить 404 при повторном чтении.
ID извлекается из ответа сервера; скрипт не предполагает пустую базу.

### Набор 2 — регистрация, вход и обработка ошибок

Полные команды находятся в `scripts/demo-errors.sh`.

```bash
BASE_URL=http://localhost:8081 bash scripts/demo-errors.sh
```

Последовательность: зарегистрировать пользователя с уникальным email,
проверить повторную регистрацию, выполнить вход, отправить неправильный
пароль, проверить неизвестного пользователя и некорректные запросы.
Каждый HTTP-код автоматически сравнивается с ожидаемым.

Оба набора запускаются из отдельного терминала при работающем приложении.
Используются bash, curl и python3. Адрес можно задать переменной `BASE_URL`.
